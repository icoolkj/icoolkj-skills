# YAML Bootstrap and Seed Data

Use this convention when a backend needs repeatable system initialization data such as framework roles, permissions, navigation or default organization metadata. It defines application bootstrap behavior, not PostgreSQL schema creation.

## Responsibility Split

- Store declarative values and relationships in versioned YAML under `backend/app/seeds/`.
- Store database operations in `backend/app/sql/bootstrap/`, using the existing SQL loader, repository and `-- @id: query_name` markers.
- Keep Python as the orchestration layer: load and validate the YAML, prepare IDs and derived values, call repository operations in order, and control the transaction.
- Keep PostgreSQL DDL and schema migrations in the locations defined by `icoolkj-platform-web-database`; do not create or alter schema as part of a data seed.
- Never store passwords, API keys, tokens or other secrets in YAML. Read initial credentials from the established environment or secret provider and hash passwords through the project's existing password service.

## YAML Contract

- Give the document an explicit schema version and validate its root sections, types and required fields before opening the write transaction.
- Reject duplicate YAML keys, duplicate stable codes, missing references, invalid parent links and parent cycles. Validate that role assignments reference configured permissions and navigation entries.
- Keep seed values declarative. Do not encode SQL, Python expressions, environment-specific secrets or historical project notes in the YAML.
- Use stable logical codes for matching existing seeded rows; generate database primary keys with the project's Snowflake ID mechanism rather than placing environment-specific IDs in the YAML.
- Fail with a clear validation error before performing any database write when the document is malformed or internally inconsistent.

## SQL and Python Contract

- Reuse the project's `bootstrap_repository`/`SqlRepository` and query-ID mechanism. Do not add a second SQL loader or inline business SQL in the bootstrap service.
- Put one-table operations in SQL files named after the physical table. Put joins or multi-table bootstrap operations in `backend/app/sql/bootstrap/queries/`, grouped by business operation.
- Bind all values as parameters. Keep authorization, uniqueness and tenant/organization constraints in SQL and service checks as required by the existing schema.
- Preserve current idempotency decisions, transaction scope, password hashing, Snowflake ID generation, security validation, ordering and exception behavior when moving constants into YAML.
- Keep writes in a single transaction when the existing initialization workflow is atomic; roll back on any failure and surface a useful error to the CLI.

## Invocation and Verification

- Expose a standalone operator-friendly CLI command for initialization, optionally allowing an explicitly supplied seed path for controlled environments.
- Do not run initialization implicitly in FastAPI lifespan, application import, or normal web startup. Operators should run schema migrations first, then invoke the bootstrap command deliberately.
- Test valid seed loading, duplicate keys/codes, malformed values, broken references and invalid navigation or organization relationships.
- Test a clean bootstrap, a repeated bootstrap, transaction rollback on repository failure, preservation of authorization/security checks, and that web startup performs no bootstrap writes.
- Document the CLI command, configuration source for initial credentials, seed-file location and migration/bootstrap order in the project's operational documentation.

## Review Checklist

- Is seed data separate from SQL behavior and schema DDL?
- Is every YAML reference valid before database writes begin?
- Does every SQL call resolve through the existing repository and a unique `@id` block?
- Are IDs generated by the framework and credentials sourced securely?
- Are idempotency, transaction rollback and existing security checks preserved?
- Is bootstrap explicit, repeatable and covered by tests rather than coupled to web startup?
