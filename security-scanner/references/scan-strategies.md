# 扫描策略详解

## 策略对比

| 维度 | quick | standard | deep |
|------|-------|----------|------|
| 文件名特征检测 | ✅ | ✅ | ✅ |
| 文件头签名检测 | ✅ | ✅ | ✅ |
| 文件哈希计算 | ❌ | ✅ | ✅ |
| 脚本内容模式匹配 | ❌ | ✅ | ✅ |
| Office 宏流检测 | ❌ | ✅ | ✅ |
| 压缩包内容检查（ZIP 文件名+文件头） | ❌ | ❌ | ✅ |
| 压缩包内容检查（RAR/7Z） | ❌ | ❌ | ⚠️ 依赖外部工具 |
| PE 导入表解析 | ❌ | ❌ | ✅ |
| LNK 目标检测 | ❌ | ❌ | ✅ |
| 递归子目录 | ✅ | ✅ | ✅ |
| 并发（--jobs > 1） | ✅ | ✅ | ✅ |
| 预计速度（1000 文件） | < 5 秒 | 10-30 秒 | 1-5 分钟 |
| 适用场景 | 快速排查 | 日常扫描 | 深度安全审计 |

## quick 策略

**检测项**：文件名特征 + 文件头签名

**适用场景**：
- 检查单个文件是否可疑
- 快速浏览目录中是否有明显威胁
- 时间紧迫的初步排查

**优势**：速度最快，几乎无 I/O 开销（仅读取文件前 1024 字节）

**局限**：
- 无法检测脚本中的危险代码
- 无法检测哈希匹配的已知恶意样本
- 无法检查压缩包内部内容
- 无法分析 PE 导入表

**执行流程**：
```
遍历目标目录（递归全部子目录）
  → 对每个文件读取前 1024 字节
  → 检查文件名特征（双扩展名、强/弱可疑关键词、随机命名、系统进程名）
  → 检查文件头签名是否与扩展名匹配
  → 分类记录结果
```

## standard 策略

**检测项**：quick 全部 + 文件哈希 + 脚本内容模式 + Office 宏流

**适用场景**：
- 日常安全扫描
- 扫描下载目录
- 扫描 U 盘
- 排查项目中的可疑脚本

**优势**：平衡速度与检测深度，覆盖大部分常见威胁

**局限**：
- 不检查压缩包内部内容
- 不分析可执行文件 PE 导入表
- 不检测 LNK 目标

**执行流程**：
```
遍历目标目录（递归全部子目录）
  → quick 全部检测
  → 计算文件 SHA256 哈希
  → 与内置 + references/hashes.json + references/hash-sources.json 合并的哈希库比对
  → 对脚本文件（JS/PS1/PSM1/VBS/VBE/BAT/CMD/PY/SH/HTA/WSF/WSH/REG）读取内容（上限 5MB）
  → 匹配危险代码模式（含 tag，用于组合语义判定）
  → 对 Office 文档检查 vbaProject.bin / OLE 宏流
  → 分类记录结果
```

## deep 策略

**检测项**：standard 全部 + 压缩包内容（含内部文件头）+ PE 导入表 + LNK

**适用场景**：
- 深度安全审计
- 检查可疑压缩包
- 分析可疑可执行文件
- 全面排查未知威胁

**优势**：检测最全面，覆盖压缩包内部、PE 导入表、LNK 目标

**局限**：
- 速度最慢
- ZIP 内检读取文件列表 + 每个条目文件头，不解压到磁盘
- RAR/7Z 内检依赖外部工具，当前版本仅提示
- PE 分析为真实导入表解析，但不做反汇编/行为分析

**执行流程**：
```
遍历目标目录（递归全部子目录）
  → standard 全部检测
  → 对 ZIP 读取内部文件列表，并读取每个条目文件头
  → 检查内部是否有可执行/脚本/双扩展名/文件头伪装
  → 对 RAR/7Z 记录"依赖外部工具，未解析"（low）
  → 对 EXE/DLL/SCR/SYS/CPL/OCX 真实解析 PE 导入表：
      DOS Header → e_lfanew → PE Signature → COFF → OptionalHeader
      → DataDirectory[1] (Import) → Section Table (RVA→Offset)
      → IMAGE_IMPORT_DESCRIPTOR → OriginalFirstThunk → API Name
  → 检查导入 API 组合（进程注入 / 下载执行）
  → 对 .lnk 校验 Shell Link 签名并搜索目标中的危险关键词
  → 分类记录结果
```

## 策略选择建议

| 场景 | 推荐策略 | 原因 |
|------|----------|------|
| 用户说"快速检查一下" | quick | 时间优先 |
| 用户说"扫描下载目录" | standard | 平衡速度与深度 |
| 用户说"深度扫描" | deep | 深度优先 |
| 单个 EXE 文件检查 | quick | 单文件无需深度 |
| U 盘扫描 | standard | 外部设备需中等深度 |
| 可疑压缩包检查 | deep | 需检查内部内容 |
| Python 项目排查 | standard | 重点检查脚本内容 |
| 全盘扫描 | standard | 文件量大，deep 过慢 |
| 安全审计 | deep | 需要最全面检测 |

## 性能预期

| 目标规模 | quick | standard | deep |
|----------|-------|----------|------|
| 1 文件 | < 0.1 秒 | < 0.5 秒 | < 2 秒 |
| 100 文件 | < 1 秒 | 3-5 秒 | 10-30 秒 |
| 1000 文件 | < 5 秒 | 10-30 秒 | 1-5 分钟 |
| 10000 文件 | < 30 秒 | 2-5 分钟 | 10-30 分钟 |

注意：
- 以上为 `--jobs 1` 串行预估，实际速度取决于磁盘 I/O 和文件大小。
- `--jobs 4~8` 对标准/深度扫描可提升 2-4 倍（I/O 密集），但在机械硬盘上可能因寻道抖动反而变慢。
- deep 策略对大文件（> 100MB）的 PE 分析会跳过（MAX_PE_SIZE = 32MB），不会显著增加耗时。
- 脚本内容分析有 5MB 上限，超限文件记录"文件过大，跳过内容分析"。

## 并发说明

- 扫描引擎使用 `ThreadPoolExecutor`，按提交顺序收集结果，进度输出加 flush。
- 单文件模式或 `--jobs 1` 时退化为串行，便于调试。
- 并发下 stderr 进度仍按完成顺序输出，与文件顺序可能不一致（仅影响可读性，不影响 JSON 结果顺序）。
